# Aster v0.12.2 — Desktop provider reliability and NVIDIA

Download **Aster-Browser-Agent-0.12.2-Windows-x64.exe** from the release assets. This is the portable **Windows desktop application**, not the Chrome extension. Extension v0.1.1 is unchanged and does not include direct NVIDIA support.

## Start or update

1. Use Windows x64 with Google Chrome installed and an internet connection.
2. Close the old Aster application, download the new EXE, and open it. No separate backend, Node.js, Python, or `.env` file is needed. Existing account-local settings remain available; do not delete your profile to update.
3. In Settings, choose Google Gemini, OpenRouter, Groq, or **NVIDIA NIM**, enter your own matching API key and exact tool-capable model ID, and validate/save.
4. Describe a task, review its limits, and approve it once. Watch Activity and the dedicated Chrome window. Generated files remain available in Downloads.

For NVIDIA, copy a hosted key and model ID from [NVIDIA's API Catalog](https://build.nvidia.com/). NVIDIA requires an explicit model ID; Aster does not guess one. OpenRouter and NVIDIA can use different IDs for the same underlying model. This integration calls NVIDIA's hosted service, not a local GPU/container. See [NVIDIA's hosted API reference](https://docs.api.nvidia.com/nim/reference/llm-apis).

## What changed

- Replaced the unexplained initial white tab with a static local waiting page. Chrome starts before the AI chooses its first browser action; the separate Chrome window is intentional for this edition.
- Added honest browser-ready/model-waiting progress and visible provider failures. An opened browser or saved key is not displayed as proof of successful inference.
- Corrected provider-specific token parameters: OpenRouter/NVIDIA use `max_tokens`; Groq uses `max_completion_tokens`.
- Added direct NVIDIA provider selection, encrypted local credential storage, exact-model validation, text/controls observations, and reuse of an existing NVIDIA environment key when only its model is missing.
- Bounded provider responses and request waits; made authentication, credits/quota, incompatible models, queued/empty replies and missing tool calls explicit. Authentication failures are not silently retried. Stop remains available.
- Preserved task approvals, browser security, upload boundaries, real downloadable files and the existing Gemini integration.
- Added a bounded packaging retry for a transient Windows lock when opening the staged executable for icon/version resource updates. Other errors still fail the build; ASAR integrity and security settings remain unchanged.

The waiting page has no task text, credentials or remote resources. Its top-level page title, text and control map are excluded from semantic model observations. Tab metadata and vision screenshots can still identify the local screen; it is not website evidence.

## Validation is not a live API guarantee

Saving credentials checks provider/model metadata without a paid inference request. NVIDIA's model catalog is public: a successful catalog lookup confirms the model ID, **not key validity**. The first approved task checks inference/account access. Current credits, quotas, permissions, tool support and response speed depend on the selected account and model.

The reported blank-tab behavior was consistent with Chrome awaiting the first model response. The inspected OpenRouter run was stopped before an action or provider error appeared; a user-specific API failure was not established. This release fixes verified startup/compatibility/error-reporting issues, not every possible provider/account failure.

## Limitations and privacy

This remains an **unsigned prototype**. Tests run on the development Windows PC, not a separate recipient machine; no guarantee is made for every website or model. Windows may show an unknown-publisher warning. Review the source and checksum; do not disable security protections.

Task/page data and screenshots for supported vision models are sent to the selected provider. Approved uploads go to the destination website. Local profiles, screenshots, recordings and generated documents can contain sensitive information. Share the EXE, not your profile, credentials, settings or task artifacts.
